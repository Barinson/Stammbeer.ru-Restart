# Stamm Brewing: архитектура нового сайта

## 0. Принципы проекта

Новый сайт Stamm Brewing проектируется как многостраничная платформа, но первый производственный инкремент строится вокруг коммерческого ядра: B2B-раздела «Бизнес», админки, локального каталога и синхронизации с МойСклад JSON API 1.2. Информационные разделы «Пиво», «Посетить пивоварню», «История» и «Контакты» подключаются позже как контентные слои поверх уже работающего ядра.

Ключевое архитектурное правило: публичный сайт никогда не делает тяжёлые live-запросы в МойСклад по клику клиента. Все товары, цены, остатки, SKU и статусы доступности сначала синхронизируются сервером в локальную базу, а публичный каталог читает только локальные данные. Ручной запуск синхронизации доступен только в админке.

## 1. Визуальная и брендовая основа

Базовая палитра должна быть зафиксирована как дизайн-токены и использоваться в публичной части и админке:

| Токен | Назначение | HEX | RGB | CMYK |
| --- | --- | --- | --- | --- |
| `--color-golden-malt` | Акцент, CTA, premium-детали, активные состояния | `#C7B166` | `199 177 102` | `0 11 49 22` |
| `--color-noble-hop` | Основной глубокий бренд-цвет, шапка, навигация, крупные блоки | `#105859` | `16 88 89` | `82 1 0 65` |
| `--color-flavorful-foam` | Светлый фирменный фон и нейтральная поверхность | уточняется по приложенной палитре | — | — |

Стиль интерфейса: современный, чистый, крафтовый, премиальный и уверенный. Любые дополнительные оттенки должны выводиться из этих цветов: затемнения Noble Hop, светлые поверхности Flavorful Foam, акцентные состояния Golden Malt, а не случайная web-палитра.

## 2. Общая архитектура проекта

### 2.1. Логические слои

```text
Публичный сайт
  ├─ Многостраничный контент: Пиво / Посетить пивоварню / История / Бизнес / Контакты
  ├─ B2B-каталог, карточка товара, корзина-заявка
  └─ SEO, OG, аналитика, формы лидов

Админка
  ├─ Контент и медиа
  ├─ Каталог и маркетинговые override-поля
  ├─ Настройки МойСклад и запуск sync
  ├─ Заявки / заказы B2B
  ├─ Пользователи, роли, аудит
  └─ SEO-управление

Backend API
  ├─ Public API для каталога, страниц, заявок
  ├─ Admin API для управления сайтом
  ├─ Integration API / jobs для МойСклад
  └─ Auth, RBAC, audit trail

Данные и инфраструктура
  ├─ PostgreSQL: локальный каталог, контент, заказы, настройки, логи
  ├─ Object storage: изображения и документы
  ├─ Redis / queue: фоновые задачи и блокировки sync
  └─ Scheduler / worker: синхронизация раз в несколько часов

МойСклад JSON API 1.2
  ├─ Товары / ассортимент / папки товаров
  ├─ Цены, SKU, коды, характеристики
  ├─ Остатки и доступность
  └─ Опционально: создание заказов покупателей на следующем этапе
```

### 2.2. Рекомендуемый технологический контур

Проект можно реализовать как монолит с чёткими модулями на старте, чтобы не раздувать инфраструктуру раньше времени:

- Frontend: SSR/SSG-фреймворк для многостраничного сайта, чтобы каталог и SEO-страницы были быстрыми и индексируемыми.
- Backend: API-модуль внутри того же приложения или отдельный сервис, если выбран стек с явным разделением frontend/backend.
- База: PostgreSQL как основной источник локального состояния сайта.
- Фоновые задачи: queue worker + scheduler, чтобы синхронизация не выполнялась в web-request.
- Файлы: S3-compatible object storage или локальное файловое хранилище для dev.
- Админка: защищённая зона `/admin`, не связанная с публичной навигацией.

На первом этапе не нужен микросервисный зоопарк. Важнее границы модулей: `content`, `catalog`, `orders`, `moysklad`, `users`, `seo`, `audit`.

## 3. Раздел «Бизнес»

Раздел «Бизнес» — рабочая B2B-витрина, а не текстовая лендинговая страница.

### 3.1. Страницы и экраны

1. `/business`
   - вход в B2B-раздел;
   - объяснение партнёрского сценария;
   - CTA «Перейти в каталог» / «Оставить заявку партнёра»;
   - преимущества для баров, ресторанов, магазинов, дистрибьюторов.
2. `/business/catalog`
   - локальный каталог товаров;
   - фильтры по типу тары, стилю, наличию, объёму, упаковке;
   - сортировка по ручному порядку показа, новизне, доступности;
   - быстрый выбор количества.
3. `/business/catalog/[slug]`
   - карточка товара;
   - маркетинговое описание, фото, характеристики;
   - данные из МойСклад: SKU/код, тара, объём, цена, остаток/доступность;
   - выбор количества и добавление в заявку.
4. `/business/cart`
   - корзина-заявка;
   - проверка минимальных партий и кратности упаковки;
   - контактные и реквизитные поля партнёра;
   - комментарий к заказу.
5. `/business/order/success`
   - подтверждение отправки заявки;
   - номер заявки;
   - обещание обратной связи менеджера.
6. Опционально позже: `/business/partners`
   - условия партнёрства;
   - документы, прайсы, зоны доставки.

### 3.2. Пользовательские сценарии

#### Новый партнёр

1. Заходит в раздел «Бизнес».
2. Смотрит условия и каталог.
3. Фильтрует продукцию по таре и наличию.
4. Добавляет позиции в заявку.
5. Заполняет контакты, ИНН/название компании, город, комментарий.
6. Получает подтверждение, а менеджер видит заявку в админке.

#### Действующий партнёр

1. Заходит сразу в каталог.
2. Использует фильтры и быстрый ввод количества.
3. Собирает повторную заявку.
4. Отправляет заказ без ожидания live-загрузки из МойСклад.
5. Получает подтверждение, заявка сохраняется локально и может быть позже передана в МойСклад.

### 3.3. Структура каталога

Каталог строится из локальной базы и содержит:

- товарные группы / папки из МойСклад;
- товары и модификации;
- тип тары: кег, банка, бутылка, короб, сет и т.д.;
- объём и единицу измерения;
- SKU / код / внешний идентификатор;
- цену для выбранного типа прайса;
- агрегированный остаток и статус доступности;
- ручной статус публикации на сайте;
- ручной порядок показа;
- маркетинговые поля сайта: описание, фото, теги, SEO, бейджи.

### 3.4. Карточка товара

Карточка должна разделять синхронизируемые и редакторские поля.

Синхронизируется из МойСклад:

- `external_id`, `meta.href`, `updated`;
- наименование;
- артикул / код;
- штрихкоды при необходимости;
- единица измерения;
- папка / группа;
- цены;
- остатки и резерв;
- архивность или признак недоступности.

Редактируется в админке сайта:

- публичный slug;
- краткое и полное маркетинговое описание;
- изображения;
- бейджи: «новинка», «сезонное», «для HoReCa»;
- SEO title/description/OG;
- публикация/скрытие;
- приоритет сортировки;
- ручной override названия, если нужно отличить витринное название от учётного.

### 3.5. Логика корзины / заявки

На первом этапе B2B-сценарий лучше реализовать как заявку, а не мгновенный оплаченный e-commerce-заказ:

- корзина хранится локально в сессии или в профиле партнёра;
- цены и доступность показываются из последнего успешного sync;
- перед отправкой заявки сервер повторно проверяет локальные остатки, но не обращается в МойСклад;
- заявка получает статус `new` и фиксирует snapshot товаров, цен, количества и доступности на момент отправки;
- администратор/менеджер обрабатывает заявку в админке;
- на следующем этапе можно добавить экспорт заявки в МойСклад как `customerorder`, если бизнес-процесс это подтвердит.

## 5. Интеграция с МойСклад JSON API 1.2

### 5.1. Источники API и предпосылки

МойСклад описывает JSON API как основной способ интеграции с внешними системами и автоматизации, включая обновление каталога, цен, остатков и выгрузку заказов с сайта. Официальная документация также указывает на наличие лимитов запросов, поэтому архитектура должна минимизировать количество обращений и использовать локальное хранение данных.

Для серверной интеграции предпочтительно использовать Bearer-токен. В публичных решениях МойСклад токен доступа к JSON API 1.2 передаётся при активации решения и используется в заголовке `Authorization: Bearer <access_token>`. Для внутреннего сайта пивоварни токен должен храниться только на сервере в зашифрованном виде или через secret storage, никогда не попадать в браузер и не использоваться публичным frontend.

Ссылки на официальные материалы:

- https://dev.moysklad.ru/ — описание возможностей JSON API и интеграций.
- https://dev.moysklad.ru/doc/api/remap/1.2/ — документация JSON API 1.2.
- https://dev.moysklad.ru/doc/api/vendor/1.0/ — правила доступа по токену, если интеграция оформляется как серверное решение.

### 5.2. Модель синхронизации

```text
Scheduler / manual admin action
  ↓
Create sync_run with status queued
  ↓
Queue worker acquires lock: moysklad-sync
  ↓
Read integration settings from DB / secrets
  ↓
Fetch product folders and products by configured source folder
  ↓
Fetch stock report for selected warehouses
  ↓
Normalize payloads into internal DTOs
  ↓
Upsert local catalog tables in transaction chunks
  ↓
Recalculate availability statuses
  ↓
Write sync_log and metrics
  ↓
Release lock and update last_success_at / last_error_at
```

Синхронизация должна быть идемпотентной: повторный запуск с теми же данными не должен создавать дубли товаров, папок, цен или остатков.

### 5.3. Периодичность

Базовый режим:

- полный каталог: раз в 6 часов;
- остатки и доступность: раз в 1–3 часа, если бизнесу нужна более частая актуализация;
- ручной запуск: только из админки, с блокировкой от параллельного запуска;
- аварийный backoff: при ошибках API увеличивать интервал повторных попыток.

Точная частота настраивается в админке и зависит от лимитов аккаунта, объёма каталога и скорости изменения остатков.

### 5.4. Какие данные забирать

Минимальный набор для первого этапа:

1. Папки товаров
   - id / href;
   - name;
   - parent folder;
   - path для навигации и фильтров.
2. Товары / ассортимент
   - id / href;
   - name;
   - code / article / externalCode;
   - updated;
   - productFolder;
   - unit;
   - salePrices;
   - attributes, если в МойСклад уже заведены полезные поля: тип тары, объём, стиль.
3. Остатки
   - assortment reference;
   - stock;
   - reserve;
   - inTransit, если используется;
   - warehouse/store, если важно разделять склады.
4. Изображения
   - на первом этапе лучше управлять изображениями в админке сайта;
   - импорт изображений из МойСклад можно добавить отдельно, если там поддерживается качественная фотобаза.

### 5.5. Выбор папки-источника

В админке хранится `source_product_folder_href` или `source_product_folder_id`. Синхронизация импортирует только товары из выбранной папки и, при включённой настройке, из её дочерних папок. Это защищает сайт от случайной публикации всего ассортимента учётной системы.

Правила:

- если товар вышел из папки-источника, локально он не удаляется физически, а получает статус `sync_hidden` или `out_of_scope`;
- ручная публикация не может показывать товар, который больше не входит в разрешённый источник, без явного override администратора;
- удаление из локальной базы — только отдельной задачей очистки после retention-периода.

### 5.6. Как не перегружать API

- Публичный сайт читает только локальную БД.
- Запросы к МойСклад выполняются только worker-ом по расписанию или вручную из админки.
- Используются пагинация, лимиты и курсор/offset в соответствии с API.
- По возможности используются фильтры по папке и `updated` для инкрементальной синхронизации.
- Остатки забираются агрегированным отчётом, а не отдельным запросом по каждому товару.
- Повторный sync не стартует, если предыдущий ещё выполняется.
- Ошибки API не блокируют публичный каталог: сайт продолжает показывать последний успешный локальный snapshot с отметкой `last_synced_at` в админке.

### 5.7. Локальный кэш и статусы доступности

Локальный каталог — это не временный cache в памяти, а основная рабочая модель сайта:

- `products` хранит стабильные локальные карточки;
- `product_sync_state` хранит техническое состояние sync;
- `inventory_levels` хранит остатки по складам или агрегированные остатки;
- `product_overrides` хранит редакторские поля;
- публичная витрина строится из read-model `business_catalog_items` или SQL view/materialized view.

Рекомендуемые статусы доступности:

- `available` — остаток выше порога;
- `limited` — остаток положительный, но ниже порога;
- `preorder` — товара нет, но он разрешён к заявке;
- `unavailable` — недоступен для заявки;
- `hidden` — не публикуется на сайте.

### 6.3. Связи

- `catalog_folders` образуют дерево через `parent_id`.
- `products` принадлежат `catalog_folders`.
- `product_variants`, `product_prices`, `inventory_levels`, `product_overrides`, `product_images` принадлежат `products`.
- `product_overrides` отделяет витринные поля от учётных данных.
- `business_orders` принадлежат `business_partners` опционально: новая заявка может создать партнёра позже после проверки менеджером.
- `business_order_items` хранят snapshot, чтобы изменение каталога после отправки не ломало историю заявки.
- `moysklad_sync_runs` связаны с логами и пользователем, если запуск ручной.

## 7. Этапы реализации

### Этап 1. Архитектурный фундамент и каркас админки

- Зафиксировать стек, модульные границы и структуру репозитория.
- Поднять базовое приложение, PostgreSQL, миграции, seed-данные.
- Добавить дизайн-токены бренда.
- Реализовать auth для админки и RBAC.
- Создать разделы админки: дашборд, каталог-заглушка, настройки МойСклад-заглушка, пользователи, SEO.
- Подготовить аудит действий.

Критерий готовности: есть защищённая админка, роли, пустая модель каталога и место для настроек интеграции.

### Этап 2. Локальная модель каталога и sync-слой МойСклад

- Реализовать таблицы каталога, настроек и sync-логов.
- Добавить безопасное хранение токена.
- Реализовать клиент МойСклад JSON API 1.2.
- Реализовать выбор папки-источника.
- Реализовать scheduled full sync и stock sync.
- Добавить ручную кнопку «Синхронизировать сейчас» в админке.
- Добавить логи, статусы, блокировку параллельных запусков и backoff.

Критерий готовности: администратор выбирает источник, запускает sync, каталог появляется локально, публичный сайт не обращается к МойСклад.

### Этап 3. Публичный раздел «Бизнес»

- Реализовать `/business`, `/business/catalog`, карточку товара, корзину-заявку и success-страницу.
- Подключить фильтры по таре, наличию, объёму и категориям.
- Подключить локальную read-model каталога.
- Реализовать отправку B2B-заявки с snapshot позиций.
- Добавить админский раздел обработки заявок.
- Добавить базовые SEO-метаданные для B2B-страниц.

Критерий готовности: партнёр может собрать заявку по локальному каталогу, менеджер видит её в админке.

### Этап 4. Управление контентом и остальные страницы

- Реализовать страницы «Пиво», «Посетить пивоварню», «История», «Контакты».
- Подключить блоки, баннеры, медиа и SEO из админки.
- Добавить формы контактов и посещения пивоварни.
- Подготовить sitemap, robots, OG-изображения.

Критерий готовности: сайт становится полноценным многостраничным брендовым ресурсом, но ядро B2B уже работает.

### Этап 5. Расширения после запуска ядра

- Экспорт подтверждённых B2B-заявок в МойСклад как заказ покупателя.
- Личный кабинет партнёра.
- Прайс-листы по ролям или типам партнёров.
- Webhook-и МойСклад как ускоритель обновления, но не как единственный источник истины.
- Импорт изображений из МойСклад, если там появится управляемая медиабаза.
- Аналитика спроса, повторные заказы, рекомендации.

## 8. Архитектурные запреты

- Не добавлять публичную кнопку «Загрузить товары».
- Не выполнять live-запросы в МойСклад из публичного пользовательского сценария.
- Не хранить токен МойСклад в frontend-коде, cookies браузера или публичных переменных окружения.
- Не импортировать весь МойСклад без выбранной папки-источника.
- Не удалять локальные товары физически сразу после исчезновения в источнике.
- Не смешивать учётные поля и маркетинговые override-поля в одной неуправляемой модели.
- Не запускать параллельные синхронизации без distributed lock.
- Не строить сначала все информационные страницы в ущерб ядру «Бизнес + админка + sync».
